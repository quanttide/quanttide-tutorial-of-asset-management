# 为什么量潮使用数百个Git仓库划分上下文？

本文介绍量潮第二大脑仓库 quanttide/quanttide 的设计思路。

## 为什么需要这么多仓库？


如果把创始人和公司十年的隐式经验榨干就需要这么多仓库。


这套上下文管理体系经过了数年的演化变成现在这样，是很多实践经验的汇总和归纳。


以“量潮数据工程手册”为例，这是一本总结我们的数据工程实践规范的工作手册，包括“数据工程”领域和“工作手册”资产两个维度。


目前在经过一系列的系统梳理和标准化以后，我们的工作领域被细分成了二十多个，标准资产也被划分成了二十多种。因此两个维度下的资产总和就是数百个。


由于旧实践向新实践的演化在不断发生，所以目前只有很少一部分仓库被创建了，还有一大部分仓库尚未整合到最新的第二大脑标准资产体系中。


## 元第二大脑的双轴结构


quanttide/quanttide 仓库 v0.1.0有 default、assets、domain 三个文件夹，每个文件夹各有一组二级第二大脑。比如，量潮工作平台（ quanttide/quanttide-platform）在 assets 文件夹里，量潮数据工程在 domains 文件夹里。


资产维度划分的是读者和作者。比如说，工作教程主要被我们用于课堂教学和内部培训，作者主要是教学团队。而工作手册则主要用于工作流程传递、蒸馏 Skill 等，作者主要是项目团队。


领域维度划分的是问题和答案，主要用于构建系统时划分功能模块，也用于划分职能和岗位。比如说，量潮数据被划分成数据工程、商务拓展、项目管理，分别对应数据工程师、商务经理和项目经理岗位。


default 文件夹放的是某个视角的默认第二大脑。比如 quanttide-founder 是创始人视角、quanttide-tech 是公司视角，可以看作一类“默认领域”，专门用来在领域划分模糊的时候先有个地方存放。


一个创始人视角的典型工作流是，我把日常的思考提交到创始人第二大脑，成熟以后转移到公司第二大脑，再成熟以后细分到量潮数据工程手册等领域资产里。


## 为复杂系统工程提供优质土壤


每个仓库的上下文边界刚好是当前 Vibe Coding 智能体的舒适区。


比如说，“量潮工作平台（quanttide/quanttide-platform）”有专门写业务需求文档（BRD）的 Skill，位置在.agents/skills/product-brd。当我需要对二十多个产品仓库轮流编辑 BRD 的时候，我只需要输入一些原始想法并且指定仓库即可。如果需要调整产品边界，也只需要指定如何调整。


再比如说，量潮数字资产云（quanttide/qtcloud-asset）是一个典型的全栈仓库，它里面包括一组文档、一组代码，还包括很多其他的辅助资产。在我们早期的实践中，这些资产都是独立仓库的。在 Vibe Coding 时代下，集中到一个仓库更有利于工程效率，因此我们放弃了过往的实践方式。


这套经过十年以来反复打磨的 Git 仓库是目前我们可以找到的最理想的上下文边界划分方式。


## 使用命名风格暗示维护思路


我们的文档仓库和代码仓库刻意使用了两套不同的风格，这样一看名字就可以知道这是什么。


文档仓库的命名格式为“quanttide-<asset>-of-<domian>”，比如量潮数据工程手册的命名为“quanttide-handbook-of-data-engineering”，暗示领域是为了工作方便的人为划分，资产及对应工作对象才是重点。


代码仓库的命名则跟随社区习惯。比如量潮数字资产云是 qtcloud-asset，量潮数据云是 qtcloud-data。


## 小结


这只是一个对全局的简单概括。资产和领域的划分还有大量的细节考虑，这些在后面再慢慢介绍。
